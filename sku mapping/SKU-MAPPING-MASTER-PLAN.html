1. Core Mental Model & Executive Summary

How Your N:1 Showroom-to-ERP Wiring Engine Works

Your domain design is already mathematically clean: every physical garment variant lives once in the canonical catalogue (products → variants.sku, matching your accountant's ERP Item Master), while every Cairo showroom (Genz, locally, lokal, mr.local, Rizz, Sash, Shopify) is wired N:1 into that single canonical variant_id via its portal barcode(s) (channel_codes) and/or exact showroom product title(s) (channel_aliases).

What Happens on Daily Sales Import

  1. Showroom sheet/API arrives with mixed seasonal codes (channel_code) or text titles (channel_product).
  2. resolveMappings() checks active channel_codes (Tier 1), then normalized channel_aliases (Tier 2), then provisional channel_list_prices (Tier 3).
  3. Matched lines stamp sales_lines.seemly_sku = variants.sku; unknown codes stay on hold / "To confirm" queue — never dropping sales or inventing SKUs.

Why It Still Felt Fragile at "97%"

  1. Code/Security Bugs Found by AuditSkill: finance blinded by wrong RLS on holds, rpc_map_unmapped_line crashing with 23505 on spacing/case twins and skipping size, collapsed alias queue groups, unindexed 500-loop batch locks, and inner RPCs callable directly.
  2. Missing Lifecycle Gates Found by Gemini Live-DB Audit: no Postgres erp_item_master table, no verified vs seeded state, no forward-only seasonal remap (vs history overwrite), and no auto-upgrade of provisional inventory lines.

5. Interactive Walkthrough — All 9 Audit Findings + Gemini Gaps → Tickets TCK-001 to TCK-010

Codebase Fixing Process & Ticket Explorer

Phase A P1 High SKU-TCK-001 — Align RLS on holds, staging & automap to is_mapping_operator_role()

Finding: SKU-AUD-001 • Canon: OWASP & Supabase RLS (wiki/14) • Schema lines: 15462, 15475, 15566, 15618

Why it happens: channel_mapping_holds, channel_alias_staging, automap_batches, and automap_actions grant SELECT via is_ops_role() (operations, customer_support), while skuMapping.edit is is_mapping_operator_role() (admin, manager, finance). So finance silently sees 0 holds in import-preview/export, and GET /api/sku-mapping/staged-aliases bypasses RLS with adminDb.

Fix & Proof: Additive migration switching those 4 SELECT policies to (SELECT public.is_mapping_operator_role()) + switching staged-aliases GET to userDb + failing SQL test proving finance sees holds & operations sees 0 rows.

Phase A P1 High SKU-TCK-002 — Harden single-edit RPC & revoke direct authenticated inner write RPCs

Finding: SKU-AUD-004 • Requires: Decision #1 • Schema lines: 2710-2819, 2826-2873

Why it happens: rpc_admin_edit_channel_mapping selects an existing code with unordered LIMIT 1 (unlike batch edit), skips the post-update multi-item lokal race guard, and omits pg_temp in search_path. Meanwhile, inner RPCs remain executable directly by authenticated, bypassing p_expected_impact and lock ordering.

Self-Check Guardrail: Builders MUST start from 20261125100000_mapping_rebuild_ops.sql so alias_move, alias_clear, code_clear, product_edit, and channel_aliases row locks are preserved.

Phase B P1 High SKU-TCK-003 — Fix rpc_map_unmapped_line normalized twin crash (23505), size write & undo snapshots

Findings: SKU-AUD-002 + SKU-AUD-008 • Schema lines: 3448-3755, 5403-5570

Why it happens: Inserting with ON CONFLICT (channel_id, code) or (channel_id, product_text) fails on normalized unique indexes (HTTP 500 23505) whenever spacing/casing differs for the same SKU; both updates omit size = v.size; and rpc_automap_apply_item/undo omits size snapshots and queries exact text instead of normalized key twins.

Fix & Proof: Deterministically look up & reactivate normalized code/alias twins, stamp size = v.size + lokal post-check, snapshot size in automap, and update tests.

Phase B P1 High SKU-TCK-004 — Stop collapsing code-less products in rpc_unresolved_sales

Finding: SKU-AUD-003 • Requires: Decision #3 • Schema lines: 8815-8882

Why it happens: rpc_unresolved_sales groups solely by (channel_id, c.name, channel_code), collapsing ALL code-less unmapped products per channel into a single card while splitting case/space-variant codes.

Fix & Proof: Partition by normalized (channel_id, key_kind, key_norm) via mapping_code_key / mapping_alias_key while keeping UI JSON keys intact.

Phase C P2 Medium SKU-TCK-005 — Functional sales_lines indexes, COLLATE "C" parity & pending staging dedup

Findings: SKU-AUD-005 + SKU-AUD-007 • Requires: Decision #2 • Schema lines: 1420-1435, 5224-5315, 7383-7553, 8444-8490, 13738

Why it happens: Batch edits run up to 500 per-channel updates against sales_lines under 8-table SHARE ROW EXCLUSIVE locks without functional indexes on mapping_code_key(channel_code) or mapping_alias_key(channel_product); inline lower(regexp_replace(...)) drifts from COLLATE "C"; channel_alias_staging can insert duplicate pending rows when casing differs.

Self-Check Guardrail: No CONCURRENTLY (single-transaction runner), use SET LOCAL lock_timeout = '5s', and start from post-20261125100000 batch/impact RPCs.

Phase C P2 Medium SKU-TCK-006 — Normalize Genz latestText & enforce Genz guard on new_sku.codes

Finding: SKU-AUD-006 • Files: src/lib/sku-mapping/genz-guard-repo.ts, mapping-edit.ts

Why it happens: latestText uses exact .eq('channel_code', code) (missing space/case variants in ledger), and codeEditsOf ignores { kind: 'new_sku', codes: { Genz: ... } } batches.

Self-Check Guardrail: Handle BOTH scalar string AND string[] in new_sku.codes.Genz (20261125100000:271-279) and keep Decision 104.5 ONE-size warning intact.
