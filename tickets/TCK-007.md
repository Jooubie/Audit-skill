# [TCK-007] Widen Bosta Deduplication Bucket or Document Boundary Gap

- **Ticket ID**: TCK-007
- **Related Finding**: [AUD-004](../findings/AUD-004.md)
- **Phase**: Phase C — Integration Resilience
- **Status**: Draft
- **Assigned Agent**: TBD (Sonnet specialist)

---

## 1. Problem Definition

When a Bosta event lacks a `timeStamp`, the deduplication key uses `floor(epochMs / 600_000)` — a 10-minute wall-clock bucket. Two identical retries arriving across a bucket boundary (e.g., 09:59 and 10:01) produce different keys and are both accepted, triggering duplicate sync runs. Per Ref 02 (Kleppmann) §2 — idempotent event processing should use deterministic identifiers, not wall-clock timestamps.

---

## 2. Expected Outcome

One of:
- **Option A**: Widen bucket to 1-hour (`3_600_000`), reducing boundary collision probability ~6×.
- **Option B**: Use Bosta-supplied `x-bosta-request-id` header when present for a deterministic key.
- **Option C**: Document and accept as a known limitation with a unit test proving the boundary behavior.

The sync itself is idempotent at the data level, so this is a resource-waste concern, not a data-corruption concern.
