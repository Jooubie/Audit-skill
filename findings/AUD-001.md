# [AUD-001] RLS Absent on `webhook_events` and `sync_runs` Tables

- **Finding ID**: AUD-001
- **Severity**: High
- **Confidence**: High
- **Category**: Security
- **Location**: `src/lib/webhooks/events-repo.ts`, `src/lib/webhooks/integrations/integrations-repo.ts`

---

## 1. Description & Evidence

The README for `src/lib/webhooks/README.md` explicitly states:

> `loadIntegrationActivity` over `sync_runs` and `webhook_events` (**RLS without policies**: the route passes the service client)

The route handlers for the integrations screen pass the **service role client** (`adminDb()`) to bypass Row-Level Security entirely, because no RLS policies are defined on these tables. This is confirmed by two separate observations:

1. The integration activity read (`loadIntegrationActivity`) uses the service client specifically to bypass an RLS configuration that has no policies — meaning any authenticated user reaching the integrations route can in principle read all rows across all tenants if the caller ever switches to the anon/user client.
2. `api/webhooks/README.md` confirms: "Primary database, service role via `adminDb()`" — the entire webhook processing path uses the service role, which completely bypasses RLS per [Ref 14, §3 Critical Caveats].

**Canon Reference**: Ref 14 (OWASP & Supabase RLS) §3 — "Activate RLS explicitly on all public schema tables during initial migration." The service role key "completely bypasses RLS rules. Never expose this key in client-side code."

---

## 2. Actual or Credible Failure Scenario

If a future refactor or bug causes the anon/user Supabase client to be passed instead of the service client to `loadIntegrationActivity`, or if a new read path is added without the service client shortcut, all tenant rows in `webhook_events` and `sync_runs` are readable without any row filter — full cross-tenant data leak. The absence of policies means RLS is a no-op even when enabled.

Additionally, since the service role key is used for all webhook writes, any Server-Side Request Forgery or accidental leakage of `adminDb()` initialization into a client-accessible path exposes full write access.

---

## 3. Technical & Business Impact

- **Technical Impact**: Cross-tenant data visibility for `webhook_events` and `sync_runs`; no defense-in-depth layer if service-client usage is ever incorrect.
- **Business Impact**: GDPR/data-isolation violation risk; regulatory exposure if tenants can observe each other's sync activity or delivery history.

---

## 4. Proposed Correction

1. Define explicit RLS policies on `webhook_events` and `sync_runs` binding to `tenant_id` or `org_id` via JWT claim:
   ```sql
   ALTER TABLE webhook_events ENABLE ROW LEVEL SECURITY;
   ALTER TABLE webhook_events FORCE ROW LEVEL SECURITY;

   CREATE POLICY "tenant_isolation_webhook_events"
     ON webhook_events
     FOR ALL
     USING (
       tenant_id = (auth.jwt() ->> 'app_metadata' ->> 'tenant_id')::uuid
     );
   ```
2. Create matching policies on `sync_runs`.
3. The integrations screen routes should switch to the user-scoped client + RLS rather than service client for reads, leaving the service client only for the webhook receipt writes that require cross-tenant authority.
4. Add additive migration with a REVERSE comment per SeemlyOps schema evolution rules.

---

- [ ] `SELECT * FROM webhook_events` as a non-admin role returns only the calling tenant's rows
- [ ] pgTAP RLS test verifying cross-tenant isolation (Ref 05 §4)
