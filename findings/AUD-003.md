# [AUD-003] `markWebhookEvents` Silently Swallows Update Failures

- **Finding ID**: AUD-003
- **Severity**: Medium
- **Confidence**: High
- **Category**: Reliability
- **Location**: `src/lib/webhooks/events-repo.ts` — `markWebhookEvents`

---

## 1. Description & Evidence

The README states:

> "`markWebhookEvents` is a no-op for an empty list and **only logs (`console.error`) when the update fails**"

This means that if the database update marking webhook events as `processed`, `coalesced`, or `error` fails (network error, constraint violation, DB timeout), the failure is silently logged and execution continues. The webhook response has already been sent (`after()` runs post-response), so there is no retry mechanism for this write failure.

**Combined with**: `sweepStuckWebhookEvents` only catches events stuck in `received` for >30 minutes — it cannot catch events that were incorrectly marked or missed entirely due to a silent `markWebhookEvents` failure.

**Canon Reference**: Ref 11 (Nygard Production Stability) — "Steady State: avoid accumulating operational debt." Silent failures that accumulate stale `received` rows create operational noise and mask real delivery problems. Ref 05 (Khorikov Testing) — observable behavior must be verifiable.

---

## 2. Actual or Credible Failure Scenario

Under a transient DB connectivity blip affecting `markWebhookEvents`:

1. Bosta sends a delivery status update; `/api/webhooks/bosta` processes it and responds 200.
2. `after()` runs `runBostaSync` successfully.
3. `markWebhookEvents` call fails silently (DB timeout); the event stays in `received`.
4. `sweepStuckWebhookEvents` runs 30 minutes later and marks it as `error`.
5. The operations team observes `error` events that were actually processed — data quality degradation in the monitoring dashboard.

Under repeated failures, the `webhook_events` table accumulates phantom `error` rows, destroying the reliability of the integration health check (`syncRunsRecorded`).

---

## 3. Technical & Business Impact

- **Technical Impact**: Incorrect event status in `webhook_events`; integration health dashboard becomes unreliable; stuck-event sweep produces false positives.
- **Business Impact**: False `error` counts in the integrations UI could trigger unnecessary support escalations or mask real delivery failures.

---

## 4. Proposed Correction

Promote `markWebhookEvents` failures from `console.error` to a structured error that is either:

1. **Returned as a result type** so callers can decide to alert/metric:
   ```typescript
   async function markWebhookEvents(
     supabase: SupabaseClient,
     ids: string[],
     status: WebhookEventStatus,
     extra?: Record<string, unknown>
   ): Promise<{ updated: number; error: Error | null }> { ... }
   ```
2. Or **emitted as a structured log event** with enough context (event IDs, status attempted) for alerting pipelines to surface it without manual log scraping.

Do **not** throw synchronously (the `after()` context does not propagate exceptions to the client), but surface failures as observable signals.

---
