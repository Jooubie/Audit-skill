# [AUD-010] Shopify BOM Preservation in `readTextCapped` May Cause HMAC Mismatch Under Reverse Proxy Normalization

- **Finding ID**: AUD-010
- **Severity**: Low
- **Confidence**: Low
- **Category**: Security / Reliability
- **Location**: `src/lib/webhooks/capped-body.ts` — `readTextCapped`

---

## 1. Description & Evidence

The README documents:

> "The body is decoded with `ignoreBOM: true`, so a leading BOM is kept and re-encoding reproduces the received bytes"

`ignoreBOM: true` in the `TextDecoder` API means the BOM character (`\uFEFF`) is **not stripped** — it is preserved in the decoded string. The intent is that `re-encoding reproduces the received bytes`, which is correct for HMAC validation where the HMAC is computed over the raw bytes.

However, the HMAC validation in `verifyShopifyHmac` takes the **raw body** (bytes) and computes SHA-256. If `readTextCapped` returns a **string** (with BOM preserved as a character), and the HMAC is computed by re-encoding the string back to bytes, the round-trip is only lossless if the encoding is identical. Node.js `TextEncoder` always uses UTF-8 without BOM — so a BOM that was part of the original bytes as `EF BB BF` (UTF-8) would survive the round-trip correctly, but a BOM in a UTF-16 body (which a misconfigured Shopify webhook might send) would not round-trip correctly.

This is a low-confidence finding because Shopify webhooks are always UTF-8, making the BOM scenario unlikely. However, the interaction between `ignoreBOM: true` and HMAC verification is not explicitly tested against adversarial BOM injection.

**Canon Reference**: Ref 14 (OWASP) §1 — "Mandate context-aware output encoding." Ref 11 (Nygard) — Defensive implementation.

---

## 2. Actual or Credible Failure Scenario

An attacker or misconfigured proxy prepends a UTF-8 BOM to a Shopify webhook body. The HMAC check succeeds (the BOM was included in Shopify's HMAC). The application processes the webhook normally. However, if the BOM causes downstream JSON parsing to fail silently (some JSON parsers reject BOM-prefixed input), the event is recorded but the payload is not processed — a silent ingestion failure.

---

## 3. Technical & Business Impact

- **Technical Impact**: Potential JSON parse failure on BOM-prefixed Shopify payloads; edge case in HMAC round-trip behavior.
- **Business Impact**: Low — Shopify does not send BOM-prefixed webhooks in practice.

---

## 4. Proposed Correction

Add an explicit unit test for `readTextCapped` that:
1. Sends a BOM-prefixed UTF-8 body
2. Verifies HMAC computed over re-encoded string matches HMAC over raw bytes
3. Verifies JSON.parse succeeds on the decoded string

This documents the actual behavior and catches any regression if the TextDecoder option changes.
