# [AUD-007] Architecture: `src/lib/` Contains Business Logic Mixed with Infrastructure — Clean Architecture Boundary Violation

- **Finding ID**: AUD-007
- **Severity**: Medium
- **Confidence**: Medium
- **Category**: Architecture
- **Location**: `src/lib/webhooks/`, `src/lib/sync/`, `src/lib/shopify/`, `src/lib/imports/`

---

## 1. Description & Evidence

The canonical target-codebase blueprint (§5.1) defines:

```
src/server/services/   # Business logic domain layer & microservice SDKs
src/lib/               # Shared core utilities, helpers, and base logic
```

However, the README files reveal that `src/lib/` contains:
- **Domain business logic**: `runBostaSync`, `runShopifySync`, `processShopifyWebhookEvent`, `refreshAnalyticsAfterLedgerWrite` (all in `src/lib/sync/` and `src/lib/webhooks/shopify-store-sync.ts`)
- **Data access repositories**: `events-repo.ts`, `running-sync-repo.ts`, `integrations-repo.ts`
- **External integration clients**: `src/lib/shopify/client`, `src/lib/shopify/auth`
- **Infrastructure adapters**: `src/lib/sync/supabase-adapter`

This directly contradicts the blueprint's intent of `src/lib/` as "shared core utilities" and `src/server/services/` as the domain logic layer. By co-locating domain orchestration, DAL repositories, and infrastructure adapters inside `src/lib/`, the codebase violates the Clean Architecture Dependency Rule (Ref 09): domain services should not live in the same layer as infrastructure adapters.

**Canon Reference**: Ref 09 (Clean Architecture) — "Inner domain layers have zero dependencies on frameworks, databases, or UI." Ref 01 (Ousterhout) — module boundaries should hide complexity; mixing concerns raises cognitive load.

---

## 2. Actual or Credible Failure Scenario

A developer adding a new sync feature naturally reaches into `src/lib/sync/` to add business logic, finding it already houses both domain orchestration (`runShopifySync`) and infrastructure adapters (`supabase-adapter`). They add a new feature that directly imports from the adapter in the same `lib/` layer — bypassing any chance of injecting a test double. This makes the new sync logic untestable without a live database (violating Ref 05).

Over time, `src/lib/` becomes an unstructured dumping ground where the boundary between "shared utility" and "core domain service" is invisible.

---

## 3. Technical & Business Impact

- **Technical Impact**: Domain logic cannot be unit-tested without DB; boundary enforcement tooling (eslint-plugin-boundaries) cannot distinguish permitted vs forbidden imports across the layer.
- **Business Impact**: Slower onboarding; higher regression risk when modifying sync logic.

---

## 4. Proposed Correction

Migrate domain orchestration services from `src/lib/` to `src/server/services/` per the blueprint:

```
src/server/services/
  sync/
    bosta-sync.ts        ← runBostaSync (moved from src/lib/sync/)
    shopify-sync.ts      ← runShopifySync (moved)
    analytics.ts         ← refreshAnalyticsAfterLedgerWrite (moved)
  webhooks/
    shopify-store-sync.ts ← processShopifyWebhookEvent (moved)
```

Keep in `src/lib/`: only pure utilities (verify.ts, capped-body.ts, bosta-key.ts, enqueue.ts) and shared types.

This is a **refactoring-only** move (no behavior change) per Ref 06 (Fowler) — Move Function refactoring. Must be done in a dedicated commit, not mixed with feature work.

---
