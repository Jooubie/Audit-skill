# [AUD-006] Enqueue-Mode RPC Failure Silently Answers 200 — Stuck-Event Sweeper Is the Only Safety Net

- **Finding ID**: AUD-006
- **Severity**: Medium
- **Confidence**: High
- **Category**: Reliability
- **Location**: `src/lib/webhooks/enqueue.ts` — `enqueueWebhookJob`; `src/app/api/webhooks/bosta/route.ts`, `src/app/api/webhooks/shopify/[store]/route.ts`

---

## 1. Description & Evidence

The README states:

> "An RPC error logs `[webhooks/<source>] enqueue failed` (no values) and the route still answers 200; the stuck-event sweeper covers it."
> "`enqueueWebhookJob` (never throws; one fixed `[webhooks/<source>] enqueue failed` line)"

When `JOB_QUEUE=on`, the webhook route:
1. Records the event (status `received`)
2. Calls `rpc_enqueue_job`
3. If the RPC **fails**, logs one line and returns 200 to Bosta/Shopify

The event stays `received` indefinitely until `sweepStuckWebhookEvents` runs (at the next Shopify cron tick, up to however frequently the cron fires). If the cron itself is degraded or the sweeper's DB call fails (which also only logs, per AUD-003), the event is never retried — it accumulates as stuck.

**Canon Reference**: Ref 11 (Nygard Production Stability) — Circuit Breakers and Fail-Fast mechanics. Silently swallowing enqueue failures and delegating recovery to a periodic sweeper violates the fail-fast principle and creates unbounded recovery latency.

---

## 2. Actual or Credible Failure Scenario

`rpc_enqueue_job` RPC starts failing due to a DB connection pool exhaustion. All webhook deliveries during the outage are recorded as `received` and answered 200. Bosta and Shopify believe delivery is acknowledged. The stuck-event sweeper runs every N minutes, marks events as `error`. No automatic retry of the actual sync is triggered — data freshness gap accumulates silently for the duration of the DB outage plus the sweep interval.

---

## 3. Technical & Business Impact

- **Technical Impact**: Silent sync gap during queue-enqueue failures; events marked `error` by sweeper with no retry of business logic; data staleness not surfaced until monitoring catches it.
- **Business Impact**: Order sync delays; analytics dashboards reflect stale data; delivery status updates not processed.

---

## 4. Proposed Correction

**Short-term**: Return a **5xx** response to Bosta/Shopify when enqueue fails, so their retry mechanisms deliver the event again:

```typescript
if (!enqueueResult.ok) {
  console.error('[webhooks/source] enqueue failed');
  return new Response('service unavailable', { status: 503 });
}
```

Both Bosta and Shopify retry on 5xx responses, so this converts an invisible silent failure into an automatic retry with backoff on the sender's side.

**Medium-term**: Add a metric/alert on `enqueue failed` log lines so operations is notified without waiting for the sweeper.

Note: The 200 response was a deliberate design choice to avoid Shopify retries flooding the endpoint when the queue is backed up. Any change here requires a decision from Jou, as it trades retry safety for flood risk.
