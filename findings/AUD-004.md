# [AUD-004] Bosta Delivery Key Uses Wall-Clock 10-Minute Bucket — Deduplication Gap at Bucket Boundary

- **Finding ID**: AUD-004
- **Severity**: Low
- **Confidence**: High
- **Category**: Reliability
- **Location**: `src/lib/webhooks/bosta-key.ts` — `bostaDeliveryKey`

---

## 1. Description & Evidence

The README documents:

> "Bosta delivery key: `tn:state:ts` with a `timeStamp`, else `tn:state:nots:<floor(epochMs/600000)>`, so a retry in the same 10-minute bucket is a duplicate and **a new state is not**"

When a Bosta event lacks a `timeStamp`, the deduplication key uses `floor(epochMs / 600_000)` — a 10-minute wall-clock bucket. This means:

- Two identical retries arriving in **the same** 10-minute window → correctly deduplicated.
- Two identical retries arriving **across** a bucket boundary (e.g., at 09:59 and 10:01) → **both are accepted** as distinct events, potentially triggering duplicate syncs.

**Canon Reference**: Ref 02 (Kleppmann Idempotency) §2 — "Deterministic Event Processing: Out-of-order and duplicate event handling using monotonically increasing sequence numbers or vector clocks rather than wall-clock timestamps."

---

## 2. Actual or Credible Failure Scenario

Bosta sends a delivery status update without a `timeStamp` field (which the docs note is treated as `null`). The delivery notification fires at 09:59:50, and a network retry arrives at 10:00:10. Both fall into different 10-minute buckets, producing keys `tn:STATE:nots:X` and `tn:STATE:nots:X+1`. Both are inserted as new `webhook_events` rows. Both trigger `runBostaSync` for the same tracking number within seconds of each other — a duplicate sync run.

The sync is likely idempotent at the data level, but it creates unnecessary load and double-writes to the primary DB.

---

## 3. Technical & Business Impact

- **Technical Impact**: Duplicate Bosta sync runs for the same tracking number on bucket-boundary retries; `sync_runs` table shows double entries; analytics may double-count.
- **Business Impact**: Unnecessary provider API calls; potential rate-limit consumption on Bosta's side; misleading sync run counts in the integrations dashboard.

---

## 4. Proposed Correction

For events without a `timeStamp`, use a **provider-supplied idempotency key** if Bosta provides one (e.g., a request UUID header), or extend the deduplication window to a larger bucket (e.g., 1-hour floor) to reduce boundary collision probability:

```typescript
// Option A: larger bucket reduces boundary probability
const bucket = Math.floor(now / 3_600_000); // 1-hour bucket
return `tn:${tn}:state:${state}:nots:${bucket}`;

// Option B: use Bosta request ID header if present
const requestId = headers.get('x-bosta-request-id');
if (requestId) return `tn:${tn}:rid:${requestId}`;
```

Alternatively, document and accept this as a known limitation with idempotent sync semantics being the primary safeguard.
