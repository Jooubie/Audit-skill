# [AUD-002] Bosta Webhook Authentication Uses Shared Secret (Non-HMAC) with No Timing-Safe Fallback Warning

- **Finding ID**: AUD-002
- **Severity**: Medium
- **Confidence**: High
- **Category**: Security
- **Location**: `src/lib/webhooks/verify.ts` — `verifyBostaWebhook`

---

## 1. Description & Evidence

The `verifyBostaWebhook` function authenticates Bosta webhook deliveries by comparing a plain shared-secret header value (`x-seemly-webhook-key`) against `BOSTA_WEBHOOK_SECRET`. The README confirms:

> "Bosta auth: only header `x-seemly-webhook-key` (no `Authorization` fallback) must equal the supplied secret (caller passes `BOSTA_WEBHOOK_SECRET` per the comment); empty secret fails"

Shopify uses `timingSafeEqual` (Node `crypto`) for HMAC comparison — this is correctly implemented. However, the Bosta path performs a **plain string equality** comparison. If the underlying implementation uses JavaScript `===` or similar, it is **not timing-safe** and is vulnerable to timing-side-channel attacks that can recover the secret byte-by-byte under repeated measurement.

**Canon Reference**: Ref 14 (OWASP & Supabase RLS) §1 — OWASP ASVS Level 2 mandates timing-safe comparison for all authentication secrets. Ref 00 Rule 3 (Contextual Scope Specialization) — OWASP governs application-layer security controls.

---

## 2. Actual or Credible Failure Scenario

An attacker capable of sending repeated POST requests to `/api/webhooks/bosta` with controlled `x-seemly-webhook-key` values and high-resolution timing measurement (e.g., from a collocated network host or timing oracle) can mount a byte-by-byte brute-force recovery of `BOSTA_WEBHOOK_SECRET` in O(256 × keyLength) attempts rather than O(256^keyLength).

---

## 3. Technical & Business Impact

- **Technical Impact**: Potential secret extraction via timing oracle; unauthorized delivery of fake Bosta events leading to incorrect sync state.
- **Business Impact**: Fake delivery status events could cause the app to prematurely mark shipments as delivered or failed, corrupting order state and triggering incorrect customer notifications.

---

## 4. Proposed Correction

Replace the plain equality check in `verifyBostaWebhook` with Node's `timingSafeEqual` (already imported for Shopify HMAC verification):

```typescript
import { timingSafeEqual, createHash } from 'crypto';

export function verifyBostaWebhook(headers: Headers, secret: string): boolean {
  if (!secret) return false;
  const provided = headers.get(BOSTA_WEBHOOK_HEADER);
  if (!provided) return false;
  // Use fixed-length hash buffers to prevent length-leak side channel
  const a = createHash('sha256').update(provided).digest();
  const b = createHash('sha256').update(secret).digest();
  return timingSafeEqual(a, b);
}
```

This is a minimal, bounded change that does not alter the logical authentication contract.
